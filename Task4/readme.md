## Архитектурное решение по логированию

### Какие логи собирать и их уровень

- FATAL — отказ сервиса или оборудования.
- ERROR — ошибочное состояние. Например, «Пользователь заблокирован».
- WARN — состояние, которое близко к нестандартному поведению системы. Например, «Пользователь неправильно ввёл пароль».
- INFO — это штатное поведение. Такие логи обычно используют для записи обычных сообщений. Например, «Данные загружены».
- DEBUG обычно используют для отладки. На продакшн-серверах их не используют, чтобы не засорять логи лишней информацией.
- TRACE обычно используют в среде разработки и для отладки в тестовом окружении.

### Мотивация

**Для чего нужно логирование?**

Логи помогают при отладке разных компонентов приложения, а также позволяют собирать и анализировать данные о работе системы. Это помогает обнаружить ошибки. Ещё логи — это один из источников информации для мониторинга.

**Некоторые технические метрики, на которые может повлиять внедрение логирования:**

- Метрики производительности. К ним относятся время отклика, пропускная способность и частота ошибок. Определение этих показателей помогает понять, насколько хорошо работает система или приложение.
- Метрики использования ресурсов. К ним относится использование ЦПУ, памяти и дисковой системы ввода-вывода. Эти метрики позволяют понять, каким образом задействуются ресурсы системой или приложением.
- Метрики доступности. Они измеряют доступность системы, например, процент времени, в течение которого система работает, и количество случаев, когда она была недоступна.
- Метрики стабильности приложения. К ним относятся количество сессий без сбоев (crash-free session) и количество пользователей без сбоев (crash-free users).

**Некоторые бизнес-метрики, на которые может повлиять внедрение логирования:**

- Вовлечённость пользователей. Мониторинг позволяет оценить, насколько пользователи пользуются приложением, какие функции используют чаще всего.
- Удовлетворённость клиентов. Мониторинг помогает понять, как те или иные решения влияют на пользователя и бизнес.
- Общая выручка и прибыль. Мониторинг позволяет оценить, сколько денег зарабатывает программа, сколько человек оплатили подписку, каковы средние и медианные чеки на клиента.

**Приоритет внедрения логирования**

Так как невозможно сразу настроить логирование для всех сервисов, приоритет отдаётся следующим:

- **Shop API** - основная точка входа заказов.
- **CRM API** - сервис обработки заказов, важно для клиентского сервиса.
- **RabbitMQ** - очереди RabbitMQ могут терять сообщения.

### Предлагаемое решение

1) Настроить Prometheus и Grafana для сбора метрик.
2) Настроить стек ELK для централизованного сбора логов.

**Политика безопасности логов**
- Исключить хранение персональных данных в логах.
- Ограничить доступ к логам по ролям с аутентификацией.
- Шифровать логи и передавать их только по защищённым каналам.
- Удалять логи со временем.

**Политика хранения логов**
- Создавать отдельные индексы по категориям, по дням, а также по уровням ошибок и др. С отдельными индексами системе удобнее работать и они занимают меньше места на диске.
- Периодически удалять индексы.
- Настроить шардирование.
- Использовать политику управления индексами — ILM.

### Анализ логов и алертинг
- Автоматические уведомления. Kibana + Telegram API (Jira API, etc). Быстрое реагирование на критические ошибки.
- Автоматический алертинг. Kibana Watcher / Grafana Alerts. Уведомления о сбоях API, RabbitMQ, SQL.
- Мониторинг в реальном времени. Grafana + Kibana Dashboards.
- Поиск аномалий. Elasticsearch ML + Loki Heuristics. Обнаружение DDoS, резкого роста заказов.
