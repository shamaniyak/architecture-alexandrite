## Архитектурное решение по кешированию

### Что можно закешировать?

- Данные каталога товаров (Shop API).
- Данные о заказах (CRM API).
- Данные пользователей (аутентификация, личный кабинет).

### Мотивация

Основные проблемы, которые решает кеширование:
- Высокая доступность данных, или high availability. Благодаря репликации данных и механизмам аварийного переключения, кеширование гарантирует высокую доступность данных.
- Высокая скорость работы и производительность приложений.  
Это достигается за счёт хранения часто используемых данных в памяти на нескольких серверах, расположенных близко к пользователям.
- Проще масштабирование.  
Распределённое кеширование упрощает масштабирование приложений, позволяя легко добавлять новые узлы кеша по мере увеличения нагрузки. В облаке это можно сделать в несколько кликов или вообще автоматически. Такое решение обеспечит непрерывную работу приложения даже при высоких нагрузках.
- Ниже затраты.  
Распределённое кеширование помогает экономить затраты за счёт снижения нагрузки на основные базы данных и оптимизации использования ресурсов: базы данных в обслуживании и настройке сильно дороже кеширования. Это позволяет приложениям выполнять больше задач с меньшими затратами.

### Предлагаемое решение

Будем использовать серверное кеширование с Redis.

Для чтения будем использовать паттерн Read-Through, т.к. с ним меньшая сложность приложения и низкая вероятность ошибок.

Для записи будем использовать Write-Through. У него следующие особенности:
- низкая стоимость,
- консистентность данных.  
Минус только один - задержка в передаче данных.

Для статической информации на фронтенде будем использовать клиентское кеширование.

**Стратегия инвалидации**

- На фронтенде будем использовать инвалидацию по времени, т.к. статическая информация редко меняется.
- На бэкенде можно делать инвалидацию, основанную на запросах и на основе изменнений, когда клиенты делают запросы на изменения.
- Изменения статусов заказа можно инвалидировать по ключу, т.к. статус четко определенные данные, и меняется фактически только он.
